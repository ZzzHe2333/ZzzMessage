# ZzzMessage 多设备历史同步与三币种虚拟礼物系统

## 重要：纯本地完整历史的同步条件

完整聊天历史**只在各自设备浏览器/WebView 的 IndexedDB 中长期保存**，Go 服务器不会新建永久云端聊天历史数据库。对于未 ACK 的实时消息，Go 继续使用此前的明文临时队列（每个账号最多500条、补发期14天）；礼物交易账本和虚拟币余额由服务端永久保存。

设备 A、设备 B 登录同一个账号后：
1. A 的 WebSocket 首帧 auth 同时传递 32 位随机 deviceId。ID 按后端地址+账号保存到浏览器 localStorage。
2. B 建立 WebSocket 后发送 sync_request，Go 将新生成的随机 requestId 中继给同账号其他在线设备。
3. A 从 IndexedDB 导出该账号所有会话的历史，按时间顺序分片（每片最多4条），通过 WebSocket 送往 B。
4. B 按账号+服务器+房间+消息ID落盘去重后，对每片返回 sync_chunk_ack。A 收到确认才继续发送下一片；结束后发送 sync_done。
5. 中继仅使用 Go 内存连接，不写入服务器聊天历史文件，消息正文在传输过程中仍对服务器可见。

**限制**：至少一个保有完整历史的其他设备要在线；如果没有，旧历史无法凭新设备或服务器临时队列之外恢复。对多源设备的合并是按消息 ID 求并集，不保证删除操作跨设备同步。设备间传输当前没有额外端到端加密，请使用 HTTPS/WSS 并仅在可信私有服务器使用。在线设备同步中断时，可在设置里点击手动重试。大量历史可能受网络、存储配额和 WebSocket 分片时限影响。

## 两种页面

- `/money`：展示金币（gold）、银币（silver）、铜币（copper）三个独立余额、登录奖励概率和最近一次奖励。每日奖励自动发放，无需领取按钮。
- `/gift`：6种虚拟礼物、选择收礼人、购买并赠送、余额扣除和双方赠礼账本。

奖励规则：**每天首次登录随机获得且仅获得 1 枚虚拟货币**，其中金币概率 1%、银币 9%、铜币 90%。Go 服务端使用加密安全的随机数产生器在 100 个等概率整数中抽取，不由客户端决定币种。以 UTC 日期为准，同账号每天只发一次；首次注册成功进入应用也计为首次登录，后续密码登录自动发放。已有会话下每天再次打开 Web/iPhone PWA，会通过已认证的 POST /api/money/daily 自动检查并发放，而非要求手动点击。币种不与人民币或任何实际货币挂钩，不能充值、提现、交易或兑换现金；没有支付网关。

收礼人必须是已经注册的其他用户；不能送给自己，余额不足拒绝购买，重复请求ID不会重复扣币。赠礼记录与钱包余额保存在 Go state.json（Docker 在持久卷内），客户端根据 API 获取。礼物没有现金价值，赠出后不会自动给收件人增加币种，仅记录礼物本身。

## API / WebSocket 协议

- GET /api/money：读取自己的三币余额和上次领取日期。
- POST /api/money/daily：供已持有会话的客户端自动核验当天是否发过奖励；首次发放返回 `{"claimed":true,"wallet":{...},"reward":{"currency":"copper","amount":1,"date":"2026-10-15"}}`，当天重复访问返回 `{"claimed":false,"wallet":{...}}`，始终不重复加币。正常的 `/api/auth/login` 和 `/api/auth/register` 也会自动执行当天发放；仅当该请求实际触发奖励时响应中包含 `dailyReward`。
- GET /api/gifts：获取物品目录。
- GET /api/gifts/history：自己的收礼和送礼交易记录（最近200条展示）。
- POST /api/gifts/send：{"recipient":"bob","itemId":"flower","requestId":"32位十六进制小写随机ID"}，原子扣款、原子落账。
- WebSocket auth 帧新增 deviceId；sync_request / sync_chunk / sync_chunk_ack / sync_done 用于在线同账号设备的数据中继，不经服务端永久持久化。

## 版本与安全

所有改动只提交 GitHub main 源码。未编译 Go/前端、未运行单元测试或真机验证、未发布新版本。现有 v0.2.0-beta.1 仍是旧版本。当前服务端账户密钥与聊天元数据、虚拟币钱包/赠礼账本以及**未 ACK 的暂存聊天正文**均需受保护；多设备同步的历史传输不是 E2EE。

**奖池核对：** 0～99 共 100 个等概率结果，0 对应金币、1～9 对应银币、10～99 对应铜币。每次抽取只增加对应余额 1，不进行金币/银币/铜币换算。数据在服务器钱包中持久化，数据库写入失败时不发放奖励并返回错误。

## iPhone 通知到达但看不到聊天正文：HTTP 兜底修复

Web Push 通知与 WebSocket 实时聊天是两条独立链路。DDNSTO 等内网穿透可能可以传输通知，但无法正确代理 WebSocket Upgrade。

新版增加经身份认证的 HTTP 兜底：GET /api/messages/pending 返回每账号最多 100 条未确认正文，POST /api/messages/send 发送并持久化消息，POST /api/messages/ack 在 IndexedDB 写入成功后清除该账户的待投递副本。
客户端在前台每 4 秒拉取未确认消息，切回前台也主动检查。WebSocket 正常时仍实时推送。客户端切换会话时，异步 IndexedDB 读取与期间收到的消息会按 ID 合并，避免消息被旧结果覆盖。

通知默认显示发件人及最多 120 个字符的消息摘要。点击通知后尝试打开对应房间；在 /setting 可以关闭「显示通知消息预览」。注意手机锁屏也可能显示消息正文，且推送内容需要经由 Apple 等提供方，当前没有端到端加密。敏感用户应关闭消息预览。

HTTP 补发只能恢复服务器尚未 ACK 的消息（每账号最多 500 条、14 天）。如果其他设备已经 ACK，而 iPhone 没有保留该消息，必须让保有历史的旧设备在线同步；若所有本地记录已经丢失，无法从服务器恢复完整旧历史。切勿直接删除后端 data/state.json。
